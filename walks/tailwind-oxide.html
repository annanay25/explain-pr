Bug 1: walking the tree twice

Calling scan() already walked the filesystem. Reading .files afterwards walked it again. Small projects hid this behind mtime checks. Thousands of files did not.

call scan() Walk #1. Already has the file list internally.

Extraction needs to visit every source. Throwing that visit list away and walking again was the bug.

bug .files Walk #2. Should have reused walk #1.

Even a walk that only checks mtimes is expensive once the tree is huge. The fix is “candidates = scan(); files = scanner.files”.

03

Bug 2: parallel walkers have a cover charge

A parallel filesystem walk helps a large repo and costs 20–50ms of overhead. That overhead is loud on a small repo. Oxide cannot see the future size of your tree.

tree few files Parallelism is a tax, not a win.

Thread pool startup dominates. A synchronous first walk is the right default when you do not yet know the size.

parallel overhead
tree thousands of files Parallelism pays off — on later scans.

After the first walk, Oxide knows the tree is large and can switch walkers. That is scene 04.

04

Fix: sync the first time, parallel after that

Initial scan uses a synchronous walker — fast when the tree is small. Later scans (dev mode) switch to a parallel walker. CLI skips the walk entirely when it already knows the changed files.

When the caller already knows which files changed, Oxide should extract those and skip the tree walk entirely.

05

mtime is tracked only after the first pass

A single production build should not pay to remember timestamps it will never read. Dev mode starts recording mtime on the second scan, then only re-extracts files that actually changed.

Scan 1 · no mtime
Scan 2 · start mtime
Scan 3+ · dirty only
lazy mtime map Created on scan 2, not scan 1.

Scan 2 still re-reads everything. That is the trade: a cheaper first build, one warm-up pass in dev, then dirty-only extraction.
