Vite 5 hid two environments inside one server

There was always a client, and optionally SSR. They shared too much implicit state: one mental model, two module graphs stuffed into server internals.

Frameworks that needed an extra runtime — edge, workerd, a second worker — had to fight the internals.

02

The problem: production has more rooms than client and SSR

A modern app is a set of runtimes. Vite 6 makes that set a first-class map instead of a boolean.

If production has four places code can run, the dev server should be able to name all four.
03

After: one process, N named environments

server.environments.client and .ssr stay. Authors can add more. Each environment has its own module graph, transform pipeline, and options.

04

Work happens on an environment, not on “the server”

environment.transformRequest(url) resolves, loads, and transforms against that graph. Plugins see which environment they are in instead of guessing from ssr flags.

05

Runtimes are factories, not hard-coded Node

A runtime provider packages how code executes: browser via /@vite/client, Node via a module runner, or Cloudflare’s workerd. Frameworks should not have to invent this each time.

06

Compatibility is the release strategy

The Vite 5 server API is not ripped out. Ecosystem packages that poked internals (VitePress and import glob maps, plugins reading config.build) need a migration, but apps can take Vite 6 without rewriting plugins on day one.
