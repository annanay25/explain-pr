03

Now the page reads a catalog the compactor already keeps

The compactor already writes a short catalog of each tenant’s blocks. The page reads that one file instead of listing every folder. A Scan bucket checkbox still does the old, slower listing when you need brand-new blocks.

new default Bucket catalog One file. Fast. May be a few minutes behind.

Written periodically by the compactor (the bucket index). A block uploaded after the last update will not show until the next catalog write. The page says how old the catalog is.

backup List every file anyway If the catalog is missing or broken, it falls back to the old listing.

Only “index not found” and “index corrupted” fall back. Other catalog errors still fail the request. The server logs a warning when it falls back.

checkbox Scan bucket The old full listing. Slower, but includes the newest blocks.

Use this for buckets that have no catalog, or to find blocks the catalog has not picked up yet. It also fills in size, samples, and chunks. The query param is scan_bucket=on.

04

You can now filter the list and page through it

Once the list is loaded, you can narrow it by block ID, when it was created, the time range it covers, or compaction level. The table shows 100 blocks at a time unless you ask for more.

new controls Filters Block ID, created after/before, time span, compaction level, deleted.

A block has to match every filter you set. Times can be a timestamp, the word now, or something like now-24h.

What “created” means

Created after/before use the time baked into the block ID, not the sample time range. Span filters use the block’s min and max sample time.

new table Pages 25, 50, 100, 250, 1000, or all. Header stays put as you scroll.

The page says “Blocks 1–100 of 430” and how many deleted blocks are hidden. Next/previous keep the filters you already set. Apply and Reset replace the old Reload button.

05

Extra columns still hit storage. JSON tools still get everything.

The catalog does not include size, sample count, or parent blocks. Checking those boxes downloads extra files — only for the page you are on, and never more than 1000. Scripts that ask for JSON still get the old full listing, so they do not break.

optional Extra columns Size, samples, sources, parents. Each one means extra storage reads.

Those fields are not in the catalog. The server downloads full metadata only for the blocks on the current page. If you ask for “all” plus extra columns, it caps at 1000 so it cannot become a full scan again.

for scripts JSON requests Still list every block and return all of them, like before.

If the request says it wants JSON (Accept: application/json), the server keeps the old behavior on purpose: scan storage, no pagination. A script can still opt into the catalog with scan_bucket=off.

D3

Filter in memory, then fetch extras only for this page

It walks the list it already has, keeps the matches, takes one page, then — only if you asked for extra columns — downloads those blocks’ full metadata. Never more than 1000 extra files.

how Keep matching blocks In memory. No extra storage reads.

Compares block ID (exact, not a prefix), created time, sample time range, compaction level, and deletion marks. All filters are AND. Block ID match ignores case.

how Show one page Default 100. Asking for page 99 when there are 2 pages shows page 2.

Page size 0 means “all”. A page past the end is clamped to the last page, which is why tests send page 99 and still get the last rows.

how now Download this page’s files Full metadata for the blocks you can see, not the whole tenant.

New helper LoadMetaFilesForBlocks. It does not list folders; it fetches known paths. If you asked for all rows plus extra columns, page size is forced to 1000 so this cannot become a full scan.

what you see Complete rows Size, samples, and chunks appear for this page only.

The short record is swapped for the downloaded one. JSON reports how many extra files were read — that count is the extra downloads, not the catalog read.

D4

Same URL. In a browser: catalog, then filters, then one page of 100. If the request says it wants JSON: list every file and return all blocks, like before, so existing scripts keep working.

how Catalog → filter → page Short rows in the HTML table, until you ask for extra columns.

Treated as a browser request unless the Accept header contains application/json. HTML never fills the JSON metas list.

how List every file → return all Full records, no paging, same as the old page.

B2

Who notices if this is wrong

Someone on call can miss a block the catalog has not picked up yet. A script that scrapes the HTML will lose size columns unless it opts in. A script that asks for JSON should be fine.

who People on call The page they already bookmark. Newest blocks may be missing.

The page now says the catalog was written N seconds ago. Scan bucket is how you recover. A stale catalog is the main human-visible bug.

who JSON scripts Safe if they ask for JSON. Not if they scrape the HTML table.

HTML scrapers that expected Size / Samples / Chunks will see those columns gone unless extra columns are checked. That is an intended default, not a silent JSON break.

writes the catalog Compactor This PR does not change how the catalog is written.

Only the read side moved. If the compactor is late, the page is late. Asking store-gateway for series data is a different HTTP surface and is untouched.

B3

The point is that a browser visit no longer downloads thousands of metadata files. Hold the PR if extra columns, JSON, or a missing catalog do not behave as promised.

Tests already pin those three: JSON still lists everything; extra columns with “all rows” cap at 1000 files; no catalog falls back to a live listing. Also bounce if filters on the catalog disagree with filters on a full listing for the same tenant.
