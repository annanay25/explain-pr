Adapters ask the scanner for three things

Robin Malfait’s Oxide API is small: scan() for class candidates, then files and globs so PostCSS, Vite, and webpack know what to watch.

Candidates are potential utilities. Files and globs are only there so the bundler invalidates the right things.

02

Bug 1: walking the tree twice

Calling scan() already walked the filesystem. Reading .files afterwards walked it again. Small projects hid this behind mtime checks. Thousands of files did not.

Even a walk that only checks mtimes is expensive once the tree is huge.
03

Bug 2: parallel walkers have a cover charge

A parallel filesystem walk helps a large repo and costs 20–50ms of overhead. That overhead is loud on a small repo. Oxide cannot see the future size of your tree.

parallel overhead
parallelism pays off
04

Fix: sync the first time, parallel after that

Initial scan uses a synchronous walker — fast when the tree is small. Later scans (dev mode) switch to a parallel walker. CLI skips the walk entirely when it already knows the changed files.

05

mtime is tracked only after the first pass

A single production build should not pay to remember timestamps it will never read. Dev mode starts recording mtime on the second scan, then only re-extracts files that actually changed.

Scan 1 · no mtime
Scan 2 · start mtime
Scan 3+ · dirty only
Scan 2 still re-reads everything. That is the trade: a cheaper first build, one warm-up pass in dev.
